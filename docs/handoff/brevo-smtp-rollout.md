# Brevo SMTP — LTMS implementation and deployment checklist

Decision 2026-10-08: Brevo SMTP for LTMS auth OTP, password reset, and email notifications. Keep Nodemailer provider-agnostic.

## What has already been prepared
- Shared Nodemailer transport accepts port 587 with STARTTLS; set `SMTP_REQUIRE_TLS=true` so STARTTLS is required (and can also use port 465 with implicit TLS for other providers).
- The real-delivery smoke test is `npm run test:smtp:brevo`; this is **not** a simulated unit test. It sends one innocuous test message per recipient (maximum 2) and checks SMTP acceptance.
- **Do not commit a real SMTP username/password, sender or recipient addresses.** Fill the local ignored `backend/.env` only.
- `EMAIL_NOTIFICATIONS_ENABLED=false` until outbox migration 051 and actual SMTP delivery have been tested. OTP and password-reset emails use SMTP regardless of that notification switch.

## Account-owner actions in Brevo (required)
1. Create a Brevo Free account at https://app.brevo.com (no paid subscription required for the ordinary free 300 emails/day quota).
2. Activate transactional SMTP as instructed by Brevo (account review/activation may be required).
3. Verify an authorized sender and authenticate a domain the team controls. An `@gmail.com` or `@ku.th` recipient mailbox is **not** automatically an authorized sending domain; do not impersonate either domain.
4. Open Brevo **SMTP & API → SMTP**, and copy the **SMTP login** (which may differ from the account email) and generate/copy an **SMTP key** (not the API key).
5. Do not paste any credential into Discord, Git, issue trackers or ChatGPT. Provide credentials directly in the local ignored `backend/.env`.

## Local backend/.env entries

```dotenv
SMTP_HOST=smtp-relay.brevo.com
SMTP_PORT=587
SMTP_REQUIRE_TLS=true
SMTP_USER=<SMTP Login shown by Brevo>
SMTP_PASS=<SMTP Key generated by Brevo>
MAIL_FROM="LTMS <sender@the-verified-domain.example>"
SMTP_TEST_TO=<personal-mailbox>,<university-mailbox>
EMAIL_NOTIFICATIONS_ENABLED=false
```

Use a sender belonging to a domain controlled by the team; the test recipients may be on completely different domains.

## Prove actual delivery
1. From `ltms-backend/backend`, execute `npm run test:smtp:brevo`. This checks SMTP connectivity and accepted messages, but **not** inbox receipt.
2. Open both receiving mailboxes; inspect Inbox and Spam; verify the two new `[LTMS SMTP Test]` messages actually arrived. This is the delivery acceptance criterion.
3. On a safe **test database**, try the real registration OTP flow (a test address not already registered), check `emailVerificationSent=true`, receive the six-digit OTP via the same SMTP transport, and complete verification within 10 minutes. Existing registered mailboxes cannot be registered again without a dedicated test account/address.
4. Apply migration `051_email_notification_outbox.sql` to a backed-up test DB, enable `EMAIL_NOTIFICATIONS_ENABLED=true` locally only, and trigger a verified-user critical notification plus a normal digest event. Confirm inbox delivery and preference opt-out.

## Existing accounts / login enforcement — agreed rollout policy
- Existing accounts **must remain allowed to log in**; do not set `email_verified=1` on unverified legacy accounts. Their email notification opt-in still requires genuinely verified email.
- After successful real-mail tests, enforce verified email **only for newly registered accounts**, with a migration-safe eligibility marker or explicit rollout cutoff. Never retroactively lock existing accounts.
- Frontend already contains an OTP verification/resend flow and a Login link for `EMAIL_NOT_VERIFIED` errors; integration still needs verification.
- **No login restriction has been enabled** as part of Brevo configuration. Rollout must wait for working SMTP and end-to-end tests.
