## ข้อที่ต้องแก้

### 1. endpoint 5 เส้นที่มีอยู่จริงในระบบแต่ไม่อยู่ในเอกสารเลย

ค้นทั้ง 149 หน้าไม่พบคําเหล่านี้แม้แต่ครั้งเดียว: `close-checkin`, `forfeit`,
`checkins/manual`, `checkins/me`, `referee-matches`

| เส้นทางจริง | รหัสที่โค้ดใช้เรียกตัวเอง | ใครใช้อยู่ตอนนี้ |
| --- | --- | --- |
| `POST /matches/{id}/close-checkin` | M18 | ปุ่มปิดเช็คอินของผู้จัด |
| `POST /matches/{id}/forfeit` | M17 | ผู้จัดตัดสินทีมไม่มาตามนัด → ผลเป็น walkover |
| `POST /matches/{id}/checkins/manual` | M19 | กรรมการเช็คอินแทนผู้เล่น (UC-04 E2b) |
| `GET /matches/{id}/checkins/me` | M20 | ผู้เล่นดูสถานะเช็คอินของตัวเอง |
| `GET /me/referee-matches` | B7 | หน้า "แมตช์ของฉัน" ของกรรมการ |

M17–M20 อยู่ใน `match.routes.ts` พร้อมคอมเมนต์อ้าง GUIDE/11 §10.5 แล้ว และ
frontend เรียกทั้งห้าเส้นอยู่ทุกวันนี้ ตัวเลข "107 endpoint" จึงควรเป็น 112
(หน้า 51 ระบุว่าตารางยืนตาม `98aa300` วันที่ 17 ก.ย. ซึ่งเก่ากว่าของที่ส่งมาแล้วสามรอบ)

หลังรีวิวฉบับนี้ `df506ea` เพิ่ม `PUT /tournaments/{id}/eligibility-rules` (C17b)
เข้ามาอีกเส้น รวมเป็น **113** — แต่เส้นนี้ยังเรียกไม่ได้จริง ดู `BACKEND-GAPS.md`
หัวข้อ `FE-c17b-be-reached-by`

**ที่สําคัญกว่าจํานวน:** UC-04 E2b (หน้า 30) บรรยายพฤติกรรมของ M19 ไว้เป็นข้อกําหนด
แต่ตาราง API ไม่มีแถวของมัน — ยูสเคสกับสัญญา API ไม่ชี้ไปที่เดียวกัน

### 2. สถานะ `walkover` ไม่มีอยู่ในเอกสารทั้งฉบับ

`match_results.match_result_status` ของจริงคือ
`enum('submitted','verified','disputed','rejected','walkover')`
แต่ §2.3.1 (หน้า 13) และพจนานุกรมข้อมูล MATCH_RESULTS (หน้า 110) เขียนไว้แค่ 4 ค่าแรก

ไม่ใช่ค่าที่ตายแล้ว — เป็นผลของ M17 (ทีมไม่มาตามนัด) ซึ่งเดินต่อไปถึงสายและ
ตารางคะแนนเหมือนผลปกติ · `GET /matches/{id}/result` ก็ตอบฟิลด์ `isWalkover` ออกมาด้วย

### 3. พจนานุกรม MATCH_RESULTS ขัดกับอีกสองที่ในเอกสารเดียวกัน

- หน้า 110 บอกว่า *"หนึ่งแมตช์มีได้หลายแถว แถวใหม่คือ revision ถัดไป (BR-13)"*
- §2.3.1 หน้า 13 บอกว่า *"match_id UNIQUE = UPDATE แถวเดิม"*
- ตาราง 4.1 S01 หน้า 67 บอกว่า *"ส่งซํ้า = UPDATE"*

ของจริงคือข้อหลัง: `match_results.match_id` เป็น UNIQUE index (`NON_UNIQUE = 0`)
และตอนนี้มี 12 แถวต่อ 12 แมตช์พอดี — เก็บ revision ไม่ได้
ประโยคหน้า 110 ควรตัดออก ไม่งั้นคนอ่านจะออกแบบหน้าจอ "ประวัติการแก้ผล" ที่ทําไม่ได้

### 4. §7.3 เมทริกซ์สิทธิ์ให้สิทธิ์ Admin ไว้ 4 แถวที่ระบบไม่ได้ให้

ทดสอบด้วยบัญชี `somchai@ku.th` ซึ่งมี `admin_scopes.scope_type = university_wide`
ยิงใส่ทัวร์นาเมนต์ 22 (ผู้จัดคือ 9201 ไม่ใช่เขา):

| แถวใน §7.3 | เอกสารบอก | ระบบตอบจริง |
| --- | --- | --- |
| ตัดสินข้อโต้แย้งผล | Admin ✓ | `403 NOT_ORGANIZER` |
| ดูภาพยืนยันตัวตน | Admin ✓ | `403 NOT_ORGANIZER_OR_REFEREE` |
| เชิญสมาชิก / แก้ไขทีม | Admin ✓ | `403 NOT_TEAM_LEADER` |
| แก้ไขรายละเอียดทัวร์นาเมนต์ | Admin ✓ | `403 NOT_ORGANIZER` |

ในโค้ดไม่มี "ทางลัดของแอดมิน" อยู่เลย — ทั้งโฟลเดอร์ `middlewares/` มีคําว่า admin
อยู่ที่เดียวคือใน `requireAdmin_U.ts` เอง

สองแถวนี้ยังขัดกับเอกสารของตัวเองด้วย:

- **ดูภาพยืนยันตัวตน** — ตาราง 4.1 M13 เขียนเองว่า *"documentUrl ให้เฉพาะกรรมการของแมตช์
  (NF-SE-03)"* ยืนยันแล้วว่าแม้แต่ผู้จัดที่เปิดรายการได้ก็ยังได้ `documentUrl: null`
- **แก้ไขสถิติย้อนหลัง** (Admin ✓, ORG ✓\*, REF ✓\*) — endpoint ที่ทําเรื่องนี้คือ S08
  `PATCH /matches/{id}/result` ซึ่งหน้า 71 ระบุเองว่า **อยู่นอก MVP** ไปแล้ว

ตัดสินใจได้สองทาง: แก้เมทริกซ์ให้ตรงกับระบบ หรือถือว่าเมทริกซ์คือข้อกําหนดแล้วให้
backend เพิ่มทางลัดของแอดมิน — แต่ต้องเลือกสักทาง

### 5. สัญญาของ 4 endpoint ในสไลซ์ 3 ตามของจริงไม่ทัน

ทั้งสี่ข้อนี้ frontend ใช้ของใหม่อยู่แล้ว เอกสารจึงเป็นฝ่ายที่ต้องตามมา

| รหัส | เอกสารเขียนว่า | ของจริงที่ `c43f497` |
| --- | --- | --- |
| S04 resolve | `resolution: uphold \| reject` | รับ `amend` เป็นทางที่สามด้วย พร้อม `winnerTeamId` + `scoreData` (ข้อความ validation ของ server พิมพ์เองว่า `expected one of "uphold"\|"reject"\|"amend"`) |
| M04 / M05 | คืน `{… status, mode, nextMatchId }` | คืน `loserNextMatchId`, `resultStatus`, `score`, `outcome` เพิ่มมาด้วย (B5 · migration 014) |
| M06 schedule | ต้องส่ง `scheduledTime`, `scheduledEndTime`, `venue` ครบสามช่อง | ส่งช่องเดียวก็ได้แล้ว (B9) — ส่งแค่ `venue` ย้ายสนามได้โดยไม่แตะเวลา |
| S05 result | *"Guest ผลแข่ง (เฉพาะ verified มิฉะนั้น 404)"* | เส้นนี้เป็น `optionalAuth` — ผู้เกี่ยวข้องที่แนบ token เห็นผลที่ยัง `submitted`/`disputed` ด้วย · ยืนยันแล้ว: guest ยิงแมตช์ 9 ได้ 404 แต่กรรมการของแมตช์ได้ 200 พร้อม `"status":"disputed"` · คําตอบจริงมีฟิลด์ `status` และ `isWalkover` ที่ไม่ได้อยู่ในเอกสาร |

### 6. UC-04 E2b บอกว่าเขียนสถานะ `success` แต่โค้ดเขียน `exception`

หน้า 30: *"ผลลัพธ์ MATCH_CHECKINS.match_checkin_status = success (API: checked_in)"*

ของจริง `POST /matches/{id}/checkins/manual` เขียน `exception` ลงฐานข้อมูล แล้ว
`toCheckinStatusApi()` ค่อยแปลงเป็น `checked_in` ตอนตอบ — ดูจากนอกเหมือนกัน
แต่ในฐานข้อมูลคนละค่า (แมตช์ 12 ตอนนี้มีแถว `exception` อยู่ 3 แถว)

ค่านี้ไม่ใช่รายละเอียดปลีกย่อย เพราะ **มันคือค่าที่ทําให้กรรมการถอนการเช็คอินไม่ได้**
— `match.repo.rejectCheckin` แก้เฉพาะแถวที่เป็น `pending` แถว `exception` กับ `success`
ตอบ `409 ALREADY_DECIDED` ทั้งคู่ (ยิงจริงกับแถว 20 และ 21 ของแมตช์ 12)

เกี่ยวพันกัน 2 จุด:

- §2.3.1 ไม่มีหัวข้อสถานะของ MATCH_CHECKINS เลย ทั้งที่มี 4 ค่า
  (`success` / `rejected` / `exception` / `pending`) และ UC-04 พึ่งมันทั้งยูสเคส
- ตาราง 4.1 M15 เขียนแค่ *"ตรวจไม่ผ่านต้องระบุเหตุผล"* ไม่ได้บอกว่าใช้ได้เฉพาะแถวที่
  ยังรอตรวจ — คนอ่านเอกสารจะออกแบบปุ่ม "ถอนการเช็คอิน" ที่กดแล้วพังทุกครั้ง
  (เราเจอเองมาแล้ว รายละเอียดอยู่ใน `FEAT-1-REMAINING.md` ข้อ `FE-check-has-gone-through`)

### 7. กฎ 404 ใน §4.2.2 ไม่ตรงกับของจริง

หน้า 49: *"404 ไม่พบทรัพยากร (รวมทัวร์ private ที่ผู้เรียกไม่ใช่ ORG/ADM)"* — เขียนไว้ว่า
ซ่อนเฉพาะทัวร์ `private`

ของจริงทัวร์ `completed` ก็ถูกซ่อนด้วย: `GET /tournaments/12` (สถานะ `completed`)
ตอบ `404 TOURNAMENT_NOT_FOUND` ให้ guest ขณะที่ `GET /tournaments/12/winner` ตอบ 200
พร้อมชื่อแชมป์ และ `/matches` กับ `/standings` ก็ 200 ปกติ

แปลว่าคนที่เพิ่งแข่งจบเปิดหน้าทัวร์ของตัวเองไม่ได้ แต่เปิดหน้าผู้ชนะได้ ทั้งที่ S10
ออกแบบมาให้ใช้กับทัวร์ `completed` โดยเฉพาะ ต้องเลือกว่าจะแก้โค้ดหรือแก้เอกสาร
