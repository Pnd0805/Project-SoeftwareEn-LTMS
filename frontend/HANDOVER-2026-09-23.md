## 1. What is now waiting on the backend

Four new items. Full text, with the route, the line and the live verification,
is in `BACKEND-GAPS.md`; the list went from 9 to 13.

### `FE-admin-queue-shows-undecidable-rows` — the most urgent of the four

`GET /admin/tournament-requests` returns rows the same caller is then refused
permission to approve.

- The queue filters with `adminScopeWhere` (`tournament.repo.ts:175`), which for
  a faculty admin is only `t.organizing_faculty_id = ?`.
- Approving additionally runs `adminCoversEligibility`
  (`tournament.service.ts:67`), which requires at least one faculty eligibility
  rule and every one of them to name that faculty.

Two different predicates, so the list and the guard disagree by construction.
Measured on 2026-09-23 as `admin.eng@ku.th` (faculty 1): the queue returned
three pending requests, all organised by faculty 1, **all three with no
eligibility rules at all**, and `POST /tournaments/:id/approve` answered
`403 ELIGIBILITY_OUT_OF_SCOPE` on every one. A queue in which every row refuses
is not a queue.

**What we would like.** Not that the rows disappear. A faculty admin has a
legitimate interest in knowing their own faculty has a request pending, even
when a university admin has to sign it. Send the row with `canDecide: boolean`
and a reason, and we will render it as visible-but-not-actionable. If you would
rather filter them out server-side that also fixes the 403s and we will follow
it — but say which, because we cannot tell from the outside.

**We cannot fix this on our side.** The list carries no eligibility rules, and
nothing tells the frontend the viewer's own admin scope. Any client-side filter
would be a guess, and a wrong guess hides a real request from the person who is
allowed to decide it.

### `FE-reject-skips-eligibility-scope` — please decide which way this goes

`rejectTournament` (`tournament.service.ts:310`) checks `getTournamentAdmin` but
**not** `adminCoversEligibility`, while `approveTournament` checks both. The
same admin, on the same tournament:

```
POST /tournaments/46/approve  ->  403 ELIGIBILITY_OUT_OF_SCOPE
POST /tournaments/46/reject   ->  200 {"status":"rejected"}
```

So a faculty admin can decline a request they are explicitly not allowed to
approve. Killing a request is at least as consequential as granting it, so if
eligibility scope is the right gate for one it is presumably the right gate for
both — but that is your call, not ours. We have deliberately left Decline
enabled, because the server really does allow it and hiding a working control is
its own kind of lie; the row warns instead. Tell us which way and we will match
it.

### `FE-referee-cannot-read-invited-tournament`

`getVisibleTournament` (`tournament.service.ts:178`) admits only the requester
and a covering admin to a tournament that is not `public` or `completed`.
Referees are not on that list — not while invited, and not after accepting.

But the order the product itself prescribes is *approve → appoint referees →
publish*, so a referee invitation almost always arrives while the tournament is
still `private`. Reproduced: invited 9003 to tournament 28 (`private`), then
`GET /tournaments/28` as 9003 → **404**, and the C1 notification
"คุณได้รับเชิญเป็นกรรมการ" linked straight at that page, so the screen read
*"That tournament doesn't exist"* about a tournament the letter in their hand
had just named.

**What we would like.** Let a user with a row in `tournament_referees` for that
tournament read it, at whatever status.

### `FE-viewer-admin-scope-unknown`

Nothing tells the frontend whether the signed-in user is an admin, or of what
scope. `GET /me` returns `facultyId` — which faculty they *belong to*, an
unrelated fact — and no admin fields. `GET /admin/scopes` is still 404, as
`FE-whole-admin-user-surface` already records.

This is why two of the screens below have to speak conditionally. Auto-approval
on creation differs per viewer, so what happens when you press Send differs per
viewer, and the one screen that has to set expectations cannot read the one fact
that decides it.

**What we would like.** `adminScope: { scopeType, facultyId } | null` on
`GET /me`. It is a read of one row that login already has the user id for.

## 2. What changed on the frontend

Nine files. `npx tsc --noEmit -p tsconfig.app.json`, `npm run lint`,
`npx vitest run` (**43 files / 260 tests**) and `npm run build` all pass.

### R24 · The referee invitation no longer opens onto a dead end

`notificationHref` in `features/inbox/InboxPage.tsx` sent every
`relatedEntityType: 'tournament'` notification to `/t/:id`. For
`referee_invited` that page 404s most of the time, for the reason above.

The Open button is gone for `referee_invited`. What the referee actually needs —
Accept and Decline — is in the Referee appointments panel of the same page, and
was all along. It comes back the day the backend half lands.

### R25 · The confirmation after creating a tournament tells the truth

`POST /tournaments` returns `{id, status, name, autoApproved}`, but
`api/tournament.ts` declared its return type as a full `TournamentDto`, so the
last two fields were invisible to every caller. The confirmation panel told
*everyone* "is with an admin. Nothing else is needed from you right now" —
including an admin whose tournament had already been approved, who was left
waiting for themselves.

Typed as `TournamentCreatedDto`; the panel now branches. The auto-approved path
reads "Approved on the spot · Tournament created" and points at the real next
step, appointing referees.

While there: the panel also claimed "the tournament page stays closed — even to
you", which stopped being true when C17b opened own-request visibility on
20 September. Both paths now offer **Open the tournament**, and both were
confirmed to load — `private` with its Manage tab, `pending_approval` reading
"Pending review".

**For the backend team, for the record:** the rule itself is working exactly as
written. Measured across all five branches of `autoApproveIfOwnScope`:

| Creator | Scope of the tournament | Result |
|---|---|---|
| university admin | anything | `private` · `autoApproved: true` |
| faculty admin | own faculty organises, entry limited to that faculty | `private` · `autoApproved: true` |
| faculty admin | own faculty organises, entry open to every faculty | `pending_approval` |
| faculty admin | another faculty organises | `pending_approval` |
| non-admin organiser | anything | `pending_approval` |

### R27 · Organising faculty and department are one question again

The form asked for *Scope* (faculty / department) and then for an *Organising
department*. `ensureCreateReferences` allows exactly two combinations — faculty
scope means a faculty and no department, department scope means both with the
department inside that faculty — so asking separately only created a way to
answer inconsistently and collect a 400.

The Scope dropdown is gone. The form asks for a faculty, then a department whose
blank option reads "The whole faculty", and derives `scopeType` from it.
Changing the faculty clears a department that no longer belongs to it, which was
the other 400 the old form allowed. **`scopeType` is still sent, unchanged. The
API contract is untouched.**

The other pair — *who organises it* versus *which faculties may enter* — was
**not** merged, and should not be. Tournament 27 is organised by Engineering and
open to everybody, which no single control can express.

### R27a · A validation message that would not clear

Mine, introduced by the merge above and reported the same day. Making the two
selects controlled took them off `register`, and a plain `setValue` does not
re-validate — so the submit-time message "กรุณาเลือกคณะที่จัดการแข่งขัน" stayed
on screen after the user picked a faculty. Pressing send again did work, but
nothing on screen said so, and it read as *the form will not let me through at
all*. Both pickers now pass `shouldValidate: true`. There is a test that fails
without the flag.

Also: the two selects sit side by side and look identical, but only the lower
one may be left blank. The faculty placeholder now reads "Choose a faculty —
required", with a standing hint underneath, and the department is labelled
"optional". Both carry `aria-invalid`.

**Worth stating plainly, because it has come up twice:** there is no way to
create a tournament without an organising faculty, and that is the backend's
rule, not a UI choice. `ensureCreateReferences` requires `organizingFacultyId`
for both scope types, and `tournaments.scope_type` has a `university` value the
MVP does not accept. If university-wide tournaments are wanted, that starts with
a backend change.

### R27b · The form says who decides, and what changes the answer

The rule works; the form did not explain it. The default entry setting is *Every
faculty*, which sends no faculty rule at all — and `adminCoversEligibility`
requires at least one. So a faculty admin who fills the form the obvious way is
queued every single time, which from the outside looks exactly like
auto-approval being broken.

We cannot say "this one will skip the queue for *you*", for the
`FE-viewer-admin-scope-unknown` reason. So the banner states the rule
conditionally: the own-faculty case adds "If that admin is you, it skips the
queue and is approved the moment you send it", and the default case says a
faculty admin sending it still waits, and points at the setting that changes the
answer.

### R27c · The admin queue marks what it cannot decide

We cannot filter the queue, for the reasons in section 1. But once the server
has refused a row there is no reason to forget it. That row is now badged
**Above your scope**, its Approve is disabled with a title naming who must
decide it, and the refusal is explained in this page's own words rather than
echoing the backend's Thai string into an English screen. Other refusal codes
still surface in the banner, now readable.
