## 1. dismiss report — ✅ ตรงกับที่ขอ

ยิงจริงบน t19 (ผู้จัด = สมชาย) กับความเห็นของมานะ ที่ playerA1 เป็นคนรายงาน:

- ✅ report → `200 {isReported: true}` · ผู้จัดได้แจ้งเตือนครั้งเดียว · ขึ้นในคิว `?reported=true`
- ✅ `POST /tournaments/19/comments/:cid/dismiss` โดยผู้จัด → `200 {id, isReported: false}` · หลุดจากคิว · ความเห็นยังอยู่
- ✅ ผู้จัดเห็น `reportCleared: true` · คนทั่วไปไม่ได้ทั้ง `isReported` และ `reportCleared`
- ✅ **ไม่แจ้งเจ้าของความเห็น** · audit `comment_report_dismissed` ครบ (`authorUserId`, `tournamentId`)
- ✅ กดซ้ำ → `409 FEEDBACK_NOT_REPORTED` · คนที่ไม่ใช่ผู้จัด → `403 NOT_ORGANIZER` · ผู้จัดทัวร์อื่น → 403 · id ความเห็นของทัวร์อื่น → `404 FEEDBACK_NOT_FOUND`
- ✅ **รายงานซ้ำหลังปิดเรื่อง** ยังตอบ `isReported: true` (ไม่เผยว่าเคยมีคนตรวจแล้ว) แต่ **ไม่กลับเข้าคิว และไม่แจ้งผู้จัดซ้ำ**
- ✅ เจ้าของแก้ข้อความแล้ว รายงานใหม่ → **กลับเข้าคิว** (ปิดรูที่ "เขียนดี → ปิดเรื่อง → แก้เป็นข้อความแย่")

### ⚠️ ขอแก้: แอดมิน `university_wide` เห็นคิวแต่ปิดเรื่องไม่ได้
ยิงกับ t14 (ผู้จัด = ปกรณ์) ด้วยสมชายซึ่งเป็นแอดมินทั้งมหาวิทยาลัย:
- `GET /tournaments/14/comments?reported=true` → **200 `canModerate: true`** เห็นรายการที่ถูกรายงาน
- `POST /tournaments/14/comments/:cid/dismiss` → **`403 NOT_ORGANIZER`**

ทางเดียวที่แอดมินจะเคลียร์คิวได้คือลบ (`DELETE /admin/feedback/:id`) ซึ่งเป็นแรงกดดันแบบเดียวกับที่ commit `f1a3624` เขียนไว้เองว่าไม่อยากให้เกิด
**ขอ (เลือกหนึ่ง):**
- **ก (แนะนำ)** ให้ route นี้รับแอดมิน `university_wide` ด้วย เหมือนที่เปิดคิวให้ดูได้อยู่แล้ว · audit แยกคนกดได้จาก `user_id` อยู่แล้ว
- **ข** ถ้าตั้งใจให้เป็นของผู้จัดคนเดียว — ส่ง `canDismiss` มากับ E14 แยกจาก `canModerate` ไม่งั้น FE ต้องเดาจาก `requestedByUserId` เอง และบอกเราว่าแอดมินควรทำอะไรกับรายการที่เห็น

### คำถามเล็ก (ไม่เร่ง)
ความเห็นที่ **ผู้จัดลบ** แล้วเจ้าของเขียนใหม่ จะใช้แถวเดิม (revive) และ `is_reported` คงเป็น 1 ตามมติ 23 ก.ย. — ข้อความใหม่จึงขึ้นในคิวทันทีโดยไม่มีใครรายงานข้อความนั้น และไม่มีแจ้งเตือน (เจอเพราะรันทดสอบซ้ำบนแถวเดิม)
เข้าใจว่าตั้งใจ แต่พอ `2f072e7` ล้าง `report_cleared_at` ตอนแก้ข้อความแล้ว สองกฎนี้ดูคนละทิศกัน — ช่วยยืนยันว่าเป็นอย่างที่ต้องการ

## 2. อัปโหลดรูปโปรไฟล์ / โลโก้ทีม — ✅ ครบ

- ✅ presign `avatar` → `uploadUrl` + `objectKey` ผูกกับผู้เรียก (`avatar/9003/...`) · PUT ขึ้น MinIO ได้ 200
- ✅ `PATCH /me {avatarUrl: objectKey}` → `avatarUrl` เป็น URL เต็ม **ไม่ใช่ key ดิบแล้ว** · คนอื่นดู `GET /users/9003` ได้ URL เดียวกัน
- ✅ key ของคนอื่น → `422 AVATAR_KEY_INVALID` · key รูปแบบถูกแต่ไม่มีไฟล์ → 422 · `image/gif` → `400 UNSUPPORTED_FILE_TYPE`
- ✅ หัวหน้าทีม presign `team_logo` + `PATCH /teams/9023 {logoKey}` → `logoUrl` · สมาชิกที่ไม่ใช่หัวหน้า → `403 NOT_TEAM_LEADER` · ไม่ส่ง `teamId` → 400
- ✅ ส่ง `null` ล้างได้ทั้งสองอย่าง
- ✅ หลังตั้งค่า MinIO: รูปโปรไฟล์และโลโก้เปิดได้ **200** · โฟลเดอร์ส่วนตัวทั้งสี่ (`checkin_document` · `referee_identity` · `dispute_evidence` · `soft_filter_document`) ยัง **403** — แยกสาธารณะ/ส่วนตัวถูกต้อง

### ⚠️ ขอให้ใส่ใน notice: เครื่องที่มีอยู่แล้วต้องรัน `minio-init` เอง
ครั้งแรกที่ยิง รูปทั้งสองได้ **403** ทั้งที่ API ตอบถูกทุกอย่าง — container `ltms-minio` ของเราสร้างจาก compose ก่อน pull นี้
จึงไม่เคยได้ policy `anonymous set download` ของ `avatar/` และ `team_logo/` · `docker compose up` ธรรมดาก็ไม่รัน `minio-init` ซ้ำให้
แก้ด้วย `docker compose up --no-deps minio-init` ครั้งเดียว (ไม่สร้าง minio ใหม่ ไฟล์เดิมอยู่ครบ)
ทุกคนในทีมที่มี MinIO อยู่แล้วจะเจอแบบเดียวกัน และจะดูเหมือน FE แสดงรูปพัง — **ขอให้ notice บอกคำสั่งนี้**
