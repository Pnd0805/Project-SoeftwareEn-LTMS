# 1. `return user ?? null`

## `??` = nullish coalescing

> **"ถ้าตัวหน้าเป็น `null` หรือ `undefined` → ใช้ตัวหลัง · ถ้าไม่ใช่ → ใช้ตัวหน้า"**

```ts
return user ?? null;
// เท่ากับ
if (user === null || user === undefined) return null;
else return user;
```

## ทำไมต้องมี — `SELECT` ที่หาไม่เจอคืนอะไร

```
rows          = []
rows.length   = 0
rows[0]       = undefined     ← ไม่ใช่ null!
rows[0] ?? null = null
```

**MySQL คืน array ว่าง ไม่ใช่ `null`** → `rows[0]` เป็น `undefined`
แต่เราประกาศไว้ว่าคืน `UserRow | null` → ต้องแปลง

```
error TS2322: Type '... | undefined' is not assignable to type 'UserRow | null'.
```

| | ความหมาย |
|---|---|
| `undefined` | "ไม่มีตัวแปรนี้ / ยังไม่กำหนดค่า" |
| `null` | "มีค่า และค่านั้นคือ *ว่างเปล่า* โดยตั้งใจ" |

⇒ เลือก `null` เพราะสื่อว่า **"ค้นแล้ว ไม่เจอ"** เป็นผลลัพธ์ที่ตั้งใจ

## ⚠️ `??` ต่างจาก `||`

```
            | ??       | ||
undefined   | แทน      | แทน
null        | แทน      | แทน
0           | 0    ✅  | แทน  ❌
''          | ''   ✅  | แทน  ❌
false       | false ✅ | แทน  ❌
```

**`??` ทำงานเฉพาะ null/undefined · `||` ทำงานกับทุกค่า falsy**

**สำคัญกับโปรเจกต์นี้:**
```ts
user.total_points || 100   // ❌ คนมี 0 แต้ม กลายเป็น 100
user.total_points ?? 100   // ✅ 0 ยังเป็น 0
```
`total_points: 0`, `is_suspended: 0`, `contact_info: ''` ล้วนเป็นค่าที่ถูกต้อง

> `?.` (optional chaining) เป็นตระกูลเดียวกัน — `user?.full_name ?? 'ไม่ระบุ'`

# 2. ทำไมต้อง `Promise<UserRow | null>`

| ส่วน | เหตุผล |
|---|---|
| `Promise<...>` | ฟังก์ชัน `async` คืน Promise เสมอ |
| `\| null` | **อาจหาไม่เจอจริงๆ** — บอกความจริงกับผู้เรียก |

## `| null` บังคับให้ผู้เรียกเช็ค

```ts
const user = await findByEmail('a@b.com');
console.log(user.full_name);   // ❌ 'user' is possibly 'null'
```

พอดีกับที่ service ต้องทำอยู่แล้ว:
```ts
if (!user) throw new AppError(401, 'INVALID_CREDENTIALS', '...');
// ผ่านบรรทัดนี้ TypeScript รู้เองว่า user เป็น UserRow (narrowing)
```

## 🔴 ถ้าโกหกว่า `Promise<UserRow>` เฉยๆ

```ts
return rows[0]!;   // ! บังคับให้ผ่าน
const user = await b('x@y.com');
user.full_name.toUpperCase();   // ✅ คอมไพล์ผ่านฉลุย
```
ตอนรัน: `TypeError: Cannot read properties of undefined`

⇒ **`| null` = ยอมรับความจริงเพื่อให้ TypeScript ช่วยได้**

# 3. ⭐ generic คืออะไรกันแน่

## ✅ ความเข้าใจที่ถูกต้อง

> *"ทั้ง 2 แบบก็ไม่รู้เหมือนกันว่าในกล่องมีอะไร เพราะยังไม่ได้รันจริง"*

**ถูกต้อง 100%** — นี่คือแก่นของเรื่องทั้งหมด

## หลักฐาน: generic ไม่เปลี่ยนข้อมูลเลย

query เดียวกันเป๊ะ เปลี่ยนแค่ generic:
```
generic = RowDataPacket[]        → ค่าจริง: { aaa: 1, bbb: 'ข้อความ' }
generic = (A & RowDataPacket)[]  → ค่าจริง: { aaa: 1, bbb: 'ข้อความ' }
generic = (B & RowDataPacket)[]  → ค่าจริง: { aaa: 1, bbb: 'ข้อความ' }

r3[0].zzz = undefined   ← บอกว่ามี zzz แต่ไม่มีจริง TypeScript ก็เชื่อ
```

**mysql2 ไม่ตรวจว่าที่เขียนใน `<>` ตรงกับข้อมูลจริงไหม**

## ทำไม TypeScript ต้องให้เราบอก

```ts
'SELECT * FROM users WHERE email = ?'
```
สำหรับ TypeScript **นี่คือข้อความธรรมดา** เหมือน `'สวัสดีครับ'`
มันไม่รู้ว่า `users` คืออะไร `*` มีคอลัมน์อะไร — และตอนคอมไพล์ยังไม่มีใครต่อ MySQL ด้วยซ้ำ

## เปรียบเทียบ: กล่องพัสดุ

```
RowDataPacket             = กล่องที่เขียนข้างนอกว่า "ของจาก MySQL"
UserRow & RowDataPacket   = กล่องเดียวกัน + ติดใบรายการของข้างใน
```
**ข้างในกล่องเหมือนกันเป๊ะ** ต่างแค่ป้าย — TypeScript เปิดกล่องดูไม่ได้ จึงตัดสินจากป้ายอย่างเดียว

## ความจริงของ `<(UserRow & RowDataPacket)[]>`

| ประเด็น | ความจริง |
|---|---|
| มีผลตอนรันไหม | ❌ **ไม่มีเลย** — type หายตอน compile |
| ใครไปเอาข้อมูลจริง | โค้ด JS ของ mysql2 (ไม่ใช่ type ตัวไหน) |
| รับประกันว่ามี 20 คอลัมน์ | ❌ **ไม่** — SELECT มา 2 ก็ได้ 2 |
| กรองคอลัมน์ส่วนเกิน | ❌ **ไม่** — มาเท่าไหร่มาหมด |
| แล้วมันทำอะไร | **บอก TypeScript ให้ตรวจโค้ดที่เหลือโดยถือว่ามี 20 คอลัมน์นี้** |

## ⚠️ ถ้าข้อมูลมาไม่ครบ — ไม่มีอะไรเกิดขึ้น

```
SELECT 1 AS user_id, 'a@b.com' AS email   (มาแค่ 2 จาก 20)

u.email        = a@b.com     ← มีจริง
u.full_name    = undefined   ← TypeScript เชื่อว่าเป็น string
u.full_name.toUpperCase() → 💥 Cannot read properties of undefined
```

**ไม่มี error ตอนคอมไพล์ · ไม่มี warning · พังตอนรันอย่างเดียว**

> **บทเรียน:** `SELECT *` สำคัญ — ถ้าเลือกบางคอลัมน์ ต้องเปลี่ยน type ด้วย เช่น `Pick<UserRow, 'user_id' | 'email'>`

# 4. `&` — intersection ที่ property รวมกัน

```ts
type A = { aaa: string; ccc: number };
type B = { bbb: boolean; ccc: number };

i: A & B  →  i.aaa ✅  i.bbb ✅  i.ccc ✅     (ได้หมด)
u: A | B  →  u.ccc ✅  u.aaa ❌  u.bbb ❌     (เฉพาะที่มีร่วมกัน)
```

## ทำไมเรียก "intersection" ทั้งที่ property รวมกัน

เพราะเป็น intersection ของ **"ค่าที่เข้าเกณฑ์"** ไม่ใช่ของ property

```
กลุ่มค่าที่เป็น A ได้  ●●●●●●●●
กลุ่มค่าที่เป็น B ได้      ●●●●●●●●
                        └──┬──┘
                   A & B = ตรงที่ทับกัน
```

| | property | ค่าที่เข้าเกณฑ์ |
|---|---|---|
| `A & B` | **มากขึ้น** (รวมกัน) | **น้อยลง** (ต้องผ่านทั้งคู่) |
| `A \| B` | **น้อยลง** (เฉพาะที่มีร่วม) | **มากขึ้น** (ผ่านอันใดอันหนึ่งพอ) |

**property กับจำนวนค่าที่เข้าเกณฑ์เป็นสัดส่วนผกผันเสมอ**

## แล้วทำไมต้อง `& RowDataPacket`

mysql2 ประกาศเงื่อนไขไว้:
```ts
pool.query<T extends QueryResult>
```
`UserRow[]` เฉยๆ → ไม่ตรงเงื่อนไข → error

**`& RowDataPacket` มีไว้แค่ "ให้ผ่านด่านของไลบรารี"** ไม่ได้ให้ประโยชน์กับเรา
(ผลข้างเคียง: ลาก index signature `[column: string]: any` ติดมา → ในไฟล์ repo พิมพ์ชื่อคอลัมน์ผิดก็ไม่มีใครเตือน)

**แต่ค่าที่ออกไปข้างนอกเป็น `UserRow` เพียวๆ** → service / mapper / controller ยังปลอดภัยเต็มที่ ✅

# 5. ⭐ ทำไมต้องมี `UserRow` ในเมื่อ `RowDataPacket` ก็รับข้อมูลได้

## ✅ คุณคิดถูก — `RowDataPacket` **พอสำหรับรับข้อมูล**

แต่**ไม่พอสำหรับเอาไปใช้ต่อ**

## บั๊กจริง 5 ตัวที่จะเกิดในโปรเจกต์นี้

| # | โค้ด | `RowDataPacket` | `UserRow` |
|---|---|---|---|
| 1 | `user.fullName` (ควรเป็น `full_name`) | ✅ ผ่านฉลุย | ❌ จับได้ + *"Did you mean 'full_name'?"* |
| 2 | `user.is_suspended === false` | ✅ ผ่านฉลุย | ❌ จับได้ — `number` ≠ `boolean` |
| 3 | `const x: number = user.faculty_id` | ✅ ผ่านฉลุย | ❌ จับได้ — อาจ `null` |
| 4 | `user.gender === 'mail'` | ✅ ผ่านฉลุย | ❌ จับได้ — ไม่มีค่านี้ |
| 5 | `const s: string = user.created_at` | ✅ ผ่านฉลุย | ❌ จับได้ — เป็น `Date` |

**`RowDataPacket` = 0 บั๊ก · `UserRow` = 5 บั๊ก**

## 🔴 ข้อ 2 คือช่องโหว่ความปลอดภัยจริง

```ts
if (user.is_suspended === false) { ... }
```
MySQL คืน `0`/`1` ไม่ใช่ `false`/`true` → `0 === false` เป็น **false เสมอ**
→ **คนถูกระงับบัญชียังใช้ระบบได้** ขัด FR-UM-05

## ✅ `UserRow` ไม่ได้ใช้ "ตอนส่ง SQL"

SQL เป็นแค่ string — `UserRow` ไม่เกี่ยวเลย

**มันใช้กับทุกอย่างที่เกิด *หลัง* query คืนค่ามาแล้ว**

```
pool.query(...) ─► rows ─► service ─► mapper ─► res.json()
                     └────────┬────────┘
                    ตรงนี้ที่ UserRow ทำงาน
```

| ไฟล์ | ใช้ทำอะไร |
|---|---|
| `user.repo.ts` | **3 บรรทัด** — แค่บอกว่าคืนอะไร |
| `requireAuth.ts` | `req.user = user` · เช็ค `is_suspended` |
| `express.d.ts` | `user?: UserRow` — **ทุก endpoint ที่ล็อกอินใช้ต่อ** |
| `auth.service.ts` | `password_hash`, `user_id`, `user_type` |
| `user.mapper.ts` | อ่านทั้ง 20 field แปลงเป็น camelCase |
| service อีก 89 endpoint | Hard Filter ใช้ `birth_date`, `gender`, `year`, `faculty_id` |

**repo คือ 3 บรรทัด — ที่เหลือคือทั้งระบบ**

## ทำไมต้องคืน `UserRow` ทั้งแถว ทั้งที่ไม่แสดง `password_hash`

**เพราะ repo กับ mapper คนละหน้าที่**

```
repo    → "เอาข้อมูลทั้งแถวมาจาก DB"        ← ต้องมี password_hash!
service → "ตัดสินใจตามกฎธุรกิจ"             ← ใช้ password_hash เทียบรหัส
mapper  → "เลือกเฉพาะที่ปลอดภัยจะส่งออก"     ← ตรงนี้ต่างหากที่ตัดทิ้ง
```

```ts
// ถ้า UserRow ไม่มี password_hash → login พังทันที
const ok = await verifyPassword(password, user.password_hash);
```

```
DB (20) → UserRow (20) → service ใช้ทุกอย่าง → mapper → DTO (12 ปลอดภัย) → JSON
                                                └─ จุดกรอง
```

**`UserRow` = ความจริงจาก DB · DTO = สิ่งที่โลกภายนอกเห็น**
การมี `password_hash` ใน `UserRow` ไม่ได้ทำให้รั่ว — รั่วก็ต่อเมื่อ mapper เผลอส่งออก

# 6. `Promise<UserRow | null>` เหมือน `as` ไหม

## ✅ คล้าย — แต่ **ต่างกันตรงที่ return type ถูกตรวจ**

```
① as            → { ผิดหมด: true } as unknown as UserRow   ✅ ผ่านฉลุย
② return type   → return { ผิดหมด: true }                   ❌ error!
③ คืนไม่ครบ      → return { user_id: 1 }                     ❌ error!
```

| | ตรวจ `return` ไหม |
|---|---|
| `x as T` | ❌ ไม่ตรวจเลย |
| `function(): T` | ✅ **ตรวจทุก `return`** |

## แต่สุดท้ายก็ยังโกหกได้ — จุดอ่อนอยู่ที่ generic

```ts
const [rows] = await pool.query<(UserRow & RowDataPacket)[]>(...);  // ① ไม่มีใครตรวจ ❌
return rows[0] ?? null;                                             // ② ตรวจกับ ① ✅
// ผู้เรียกปลายทาง                                                   // ③ เชื่อ ② ✅
```

**ทั้งระบบตรวจกันเองสอดคล้อง — แต่ตั้งอยู่บนสมมติฐานเดียวที่ไม่มีใครตรวจ คือ generic**

## สรุปเปรียบเทียบ

| | ตรวจตอนคอมไพล์ | ตรวจตอนรัน |
|---|---|---|
| `pool.query<T>` | ❌ | ❌ |
| `x as T` | ❌ | ❌ |
| `function(): T` | ✅ | ❌ |
| Zod `.parse()` | — | ✅ |

**มีแค่ Zod ที่ตรวจของจริง** ที่เหลือเป็นข้อตกลงระหว่างเรากับ TypeScript

# 7. `RowDataPacket` ไม่ได้ใส่ทุก query

นิยามจริงของ mysql2:
```ts
export type QueryResult =
  | OkPacket
  | ResultSetHeader
  | ResultSetHeader[]
  | RowDataPacket[]        // ← หนึ่งใน 7
  | RowDataPacket[][]
  | OkPacket[]
  | ProcedureCallPacket;
```

## เลือกตามชนิดคำสั่ง SQL

| คำสั่ง | คืนอะไรจริงๆ | generic |
|---|---|---|
| `SELECT` | **แถวข้อมูล** | `(UserRow & RowDataPacket)[]` |
| `INSERT` | **สรุปผล** (insertId) | `ResultSetHeader` |
| `UPDATE` | สรุปผล (affectedRows) | `ResultSetHeader` |
| `DELETE` | สรุปผล | `ResultSetHeader` |

**ใช้ผิดชนิด:**
```ts
const [result] = await pool.query<RowDataPacket[]>('INSERT INTO ...');
return result.insertId;
// ❌ Property 'insertId' does not exist on type 'RowDataPacket[]'
```

**`create()` จะใช้ `ResultSetHeader` ไม่มี `RowDataPacket` เลย:**
```ts
const [result] = await pool.query<ResultSetHeader>('INSERT INTO users ...', [...]);
return result.insertId;
```

> ถามตัวเองว่า **"คำสั่งนี้คืนแถวข้อมูล หรือคืนรายงานผล"**

# ✅ `user.repo.ts` ที่ถูกต้อง

```ts
import pool from "../config/db.js";
import type { RowDataPacket, ResultSetHeader } from 'mysql2';
import type { UserRow } from "../types/db.js";

export async function findByEmail(email: string): Promise<UserRow | null> {
  const [rows] = await pool.query<(UserRow & RowDataPacket)[]>(
    'SELECT * FROM users WHERE email = ?', [email]
  );
  return rows[0] ?? null;
}

export async function findById(userId: number): Promise<UserRow | null> {
  const [rows] = await pool.query<(UserRow & RowDataPacket)[]>(
    'SELECT * FROM users WHERE user_id = ?', [userId]
  );
  return rows[0] ?? null;
}

// INSERT → ResultSetHeader ไม่ใช่ RowDataPacket
export async function create(data: NewUser): Promise<number> {
  const [result] = await pool.query<ResultSetHeader>(
    `INSERT INTO users (...) VALUES (...)`, [...]
  );
  return result.insertId;
}
```

# 📌 3 ประโยคที่สรุปทั้งวัน

1. **generic กับ return type คือคำสัญญา ไม่ใช่การตรวจสอบ** — `pool.query<T>` ไม่มีใครตรวจ, `function(): T` ตรวจแค่ว่า `return` ตรงกับที่ประกาศ
2. **type ทั้งหมดหายตอน compile** — ไม่มีตัวไหน "ไปเอาข้อมูล" หรือ "กรองข้อมูล" ตอนรัน
3. **`UserRow` มีค่าที่ 89 endpoint ข้างหน้า ไม่ใช่ที่ 3 บรรทัดใน repo**
