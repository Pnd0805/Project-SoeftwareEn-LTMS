## ภาพรวมทั้งโปรเจกต์ — คุณกำลังจะสร้างอะไร

**LTMS** = ระบบจัดการทัวร์นาเมนต์กีฬาของมหาวิทยาลัย มี 5 บทบาท:

```
Guest    → ดูทัวร์นาเมนต์สาธารณะ ดูผลแข่ง
User     → สมัครสมาชิก สร้างทีม เชิญเพื่อน สมัครแข่ง
Organizer→ ขอจัดทัวร์ เชิญกรรมการ จัดสาย อนุมัติทีม  (ไม่ใช่ role ถาวร — เป็นคนที่ขอจัดทัวร์นั้นๆ)
Referee  → เช็คอินผู้เล่น เริ่มแมตช์ บันทึกผล/สถิติ     (ไม่ใช่ role ถาวร — ผูกกับทัวร์นั้นๆ)
Admin    → อนุมัติทัวร์ อนุมัติทีม Official ระงับบัญชี  (มีแถวใน admin_scopes)
```

> **จุดสำคัญที่ต้องเข้าใจตั้งแต่ตอนนี้:** Organizer / Team Leader / Referee **ไม่ใช่ role ที่ฝังใน JWT**
> คนเดียวเป็นหัวหน้าทีม A, เป็น Organizer ของทัวร์ B, เป็นกรรมการของทัวร์ C ได้พร้อมกัน
> ดังนั้น JWT เก็บแค่ `user_id` แล้วไป**เช็คสิทธิ์ทีละ request จากฐานข้อมูล** (Part 0-1 §1.3-1.4)
> นี่คือเหตุผลที่ต้องมี middleware แยก 5 ตัว ไม่ใช่ตัวเดียวเช็ค role

## กฎ 6 ข้อที่ห้ามลืม (สรุปจาก Part 0-1 ทั้งฉบับ)

1. **DB เป็น `snake_case` / API เป็น `camelCase`** → ต้องมี mapper คั่นเสมอ **ห้ามส่ง row จาก MySQL ออกไปตรงๆ** (จะหลุด `password_hash`)
2. **ค่า enum ไม่แปลง** — `'pending_approval'`, `'Ready'`, `'onsite'` ส่งออกไปเหมือน DB เป๊ะ (มันคือ *ข้อมูล* ไม่ใช่ *ชื่อฟิลด์*)
3. **ห้ามใช้ `PATCH /resource/:id { status: "..." }` เปลี่ยนสถานะ** → ใช้ action endpoint `POST /resource/:id/approve` แทน 1 endpoint = 1 transition
4. **ตรวจสิทธิ์ฝั่ง server เสมอ** — การซ่อนปุ่มบนหน้าเว็บไม่ใช่การควบคุมสิทธิ์
5. **`requireAuth` ต้อง query `users` ทุก request** เพื่อเช็ค `is_suspended` — JWT เพิกถอนไม่ได้ ต้องเช็คสดจาก DB
6. **error message เป็นภาษาไทยที่บอกวิธีแก้** + `code` เป็นอังกฤษคงที่ให้ frontend เขียน logic
