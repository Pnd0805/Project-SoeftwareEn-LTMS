# ส่วนที่ 1 — JWT ทำงานยังไง

## 1.1 `sign` — สร้าง token

**payload ไม่ต้องประกาศ object แยกก่อน** เขียนตรงๆ ในวงเล็บได้เลย เป็น object JavaScript ธรรมดา

```ts
jwt.sign({ sub: String(userId) }, secret, { expiresIn: '7d' })
```

**คืนค่าเป็น `string` ตัวเดียว:**
```
token = eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJzdWIiOiI0MiIsImlhdCI6MTc4NzY1NTQ2MSwiZXhwIjoxNzg4MjYwMjYxfQ.tLFrvydSBhy5fyptW87_W60vmtEOiqZZZZls9EcZwKo
```

## 1.2 ข้างใน token มีอะไร — แยก 3 ส่วนด้วยจุด

```
eyJhbGciOiJI...  .  eyJzdWIiOiI0Mi...  .  tLFrvydSBhy5...
     header              payload            ลายเซ็น
```

**decode 2 ส่วนแรกได้เลย ไม่ต้องมี secret:**
```
header  → {"alg":"HS256","typ":"JWT"}
payload → {"sub":"42","iat":1787655461,"exp":1788260261}
```

- `iat` / `exp` ไลบรารีใส่ให้เองจาก `expiresIn: '7d'` เราไม่ได้ใส่
- **JWT ไม่ได้เข้ารหัส แค่เซ็นชื่อกำกับ** → ห้ามใส่ข้อมูลลับใน payload

## 1.3 `verify` — คืน object (payload เดิม)

```
verify คืนค่า : { sub: '42', iat: 1787655475, exp: 1788260275 }
typeof        : object
sub           : '42'  ← เป็น string ต้อง Number() ก่อนใช้
```

## 1.4 verify ทำ 2 งานพร้อมกัน

```
verifyToken(token)
     ├─ งานที่ 1: ตรวจลายเซ็น + วันหมดอายุ → ผิดเมื่อไหร่ throw ทันที
     └─ งานที่ 2: คืน payload กลับมา        → เอา sub ไปใช้ต่อ
```

**ทดสอบจริง — token ที่ถูกแก้ payload (ปลอม `sub` เป็น 1):**
```
❌ JsonWebTokenError - invalid signature
```

**token ที่หมดอายุ:**
```
❌ TokenExpiredError - jwt expired
```

> ⚠️ **verify ไม่ return `false` เวลาผิด — มัน `throw`**
> ⇒ ต้องมี `try/catch` ครอบใน `requireAuth`
> ⇒ `if (!decoded)` ไม่มีวันเป็นจริง (เคยเขียนผิดตรงนี้)

## 1.5 ✅ ความเข้าใจที่ถูกต้อง — payload ≠ `req.user`

**เคยเข้าใจผิดว่า:** verify ได้ payload มา → ใส่ `req.user` ได้เลย

**ที่ถูกคือ:** payload มีแค่ 3 ตัว
```
{ sub: '42', iat: ..., exp: ... }

มี full_name ไหม   : undefined
มี is_suspended ไหม : undefined
มี email ไหม       : undefined
```

แต่ `req.user` ประกาศไว้เป็น `UserRow` ซึ่งมี 20 field

**⇒ ถ้ายัด payload เข้าไป `req.user.full_name` จะเป็น `undefined` ทั้งระบบ**

### เปรียบเทียบ: token = บัตรสมาชิกที่มีแค่เลขบัตร

```
บัตรเขียนว่า "สมาชิกหมายเลข 42"     (= sub: '42')
verify = ตรวจว่าบัตรจริงไหม ปลอมไหม หมดอายุยัง
```

รู้ว่าบัตรจริง ≠ รู้ว่าเจ้าของชื่ออะไร → ต้องเอาเลข 42 ไปเปิดทะเบียน (DB) ต่อ

### ทำไมไม่ใส่ข้อมูลทั้งหมดลงบัตรเลย

1. **ข้อมูลจะเก่า** — ฝัง `is_suspended: false` ไว้ตั้งแต่วัน login แล้ววันที่ 3 โดนระงับ บัตรใบเดิมยังบอกว่าปกติ ใช้ได้ต่ออีก 4 วัน
2. **ใครก็อ่านบัตรได้** — ดูข้อ 1.2

## 1.6 วงจรเต็ม

```
① login สำเร็จ → signToken(user.user_id) → "eyJhbGci..."
② ส่ง token กลับ client
③ client เก็บไว้
④ เรียก API ครั้งต่อไป แนบ  Authorization: Bearer eyJhbGci...
⑤ requireAuth:
   ├─ ตัด "Bearer " ออก
   ├─ verifyToken(token)              → { sub: '42' }   ★ ยืนยันว่าของจริง
   ├─ userRepo.findById(Number('42')) → UserRow          ★ ไปเอาข้อมูลจริง
   ├─ เช็ค is_suspended                                  ★ เช็คสดทุกครั้ง
   └─ req.user = user
⑥ controller ใช้ req.user ต่อได้เลย
```

| | `signToken` | `verifyToken` |
|---|---|---|
| ใช้ตอนไหน | login สำเร็จ (ครั้งเดียว) | **ทุก request** ที่ต้องล็อกอิน |
| รับ | `userId: number` | `token: string` |
| คืน | `string` | `{ sub: string }` |
| ผิดแล้ว | ไม่ค่อยพลาด | **throw** ต้อง try/catch |
| หน้าที่จริง | สร้างบัตร | **ตรวจบัตรว่าปลอมไหม** |

## 1.7 ✅ เชื่อ payload ได้แค่ไหน

| | เชื่อได้ไหม | เพราะ |
|---|---|---|
| `sub` = ใคร | ✅ **เชื่อได้ 100%** | มีลายเซ็นกำกับ ปลอมไม่ได้ |
| `iat` / `exp` | ไม่ต้องแตะ | ไลบรารีเช็ค `exp` ให้แล้ว |
| ชื่อ อีเมล คณะ | — ไม่มีใน token | ต้อง query DB |
| ถูกระงับหรือยัง | ❌ **แม้ใส่ไว้ก็เชื่อไม่ได้** | ข้อมูลเก่าตั้งแต่วัน login |

> **`payload` เป็น "สะพาน" ไปหาข้อมูลจริง ไม่ใช่ปลายทาง**

# ส่วนที่ 2 — `as` (type assertion)

## 2.1 `as` คืออะไร

**`as T` = "TypeScript คิดว่าค่านี้เป็นอย่างอื่น แต่ฉันรู้ว่ามันเป็น `T` — อย่าเถียง"**

## 2.2 หลักฐาน 3 ข้อ

**① ไม่แปลงค่าเลย**
```
ก่อน as : 7d string
หลัง as : 7d string
เท่ากันไหม : true
```

**② หายไปหมดตอน compile**
```ts
// TypeScript ที่เขียน
const expireIn: string = '7d';
type ExpiresIn = '7d' | '15m' | number;
const opt = { expiresIn: expireIn as ExpiresIn };
```
```js
// JavaScript ที่ได้จริง
const expireIn = '7d';
const opt = { expiresIn: expireIn };
```
`type` หายทั้งบรรทัด · `: string` หาย · `as ExpiresIn` หาย

**③ โกหกได้ ไม่มีใครห้าม**
```ts
const lie = 'สวัสดี' as unknown as number;
console.log(lie + 1);   // → "สวัสดี1"  compile ผ่าน แต่ผลลัพธ์พัง
```

## 2.3 `as` ≠ การแปลงค่า

```
str as number  → typeof = string   ❌ แค่พูด ไม่ได้ทำ
Number(str)    → typeof = number   ✅ แปลงจริง
```

| | ทำอะไร | มีผลตอนรันไหม |
|---|---|---|
| `x as T` | บอก TypeScript ให้ถือว่าเป็น `T` | ❌ ไม่มีเลย |
| `Number(x)` | แปลงค่าจริง | ✅ มี |

# ส่วนที่ 3 — เคสจริง 2 อัน

## 3.1 `expiresIn: authConfig.expireIn as ExpiresIn`

**ปัญหา:** `expiresIn` ไม่รับ `string` ธรรมดา แต่รับ template literal type ที่แคบมาก

```ts
// @types/ms
type StringValue =
    | `${number}`                 // "604800"
    | `${number}${UnitAnyCase}`   // "7d", "15m", "24h"
    | `${number} ${UnitAnyCase}`  // "7 days"
```

`authConfig.expireIn` เป็น `string` ธรรมดา (มาจาก `requireEnv()`) → **TypeScript ไม่มีทางรู้ว่า `.env` เขียนอะไรไว้ เพราะอ่านตอนรัน ไม่ใช่ตอน compile**

**วิธีแก้ที่ใช้:**
```ts
type ExpiresIn = NonNullable<SignOptions['expiresIn']>;
// ...
{ expiresIn: authConfig.expireIn as ExpiresIn }
```

`NonNullable<>` มีไว้ตัด `undefined` ออก เพราะ `expiresIn?:` เป็น optional และ tsconfig เปิด `exactOptionalPropertyTypes: true` ซึ่งห้ามใส่ `undefined` ตรงๆ

### 🔴 บทเรียน: `as` ต้องแคบที่สุด

**เคยแนะนำผิดให้ใช้ `{...} as SignOptions`** — ทดสอบแล้วพบว่า:

```ts
{ expresIn: authConfig.expireIn } as SignOptions   // พิมพ์ผิด!
```
```
⚠️  ไม่มี error เลย — พิมพ์ expresIn ผิดก็ผ่าน!
```

**เพราะ cast ทั้ง object = ปิดการตรวจ key ทั้งหมด** → token ไม่มีวันหมดอายุ โดยไม่มีอะไรเตือน

| วิธี | คอมไพล์ผ่าน | จับ typo ได้ |
|---|---|---|
| ไม่ cast | ❌ | — |
| `{...} as SignOptions` | ✅ | ❌ **ปล่อยผ่าน** |
| `expireIn as ExpiresIn` | ✅ | ✅ **จับได้** |

> **หลัก: cast แค่ค่า ไม่ใช่ทั้งก้อน — ยิ่งขอบเขต `as` กว้าง ยิ่งเสี่ยง**

## 3.2 `jwt.verify(...) as { sub: string }`

**ทำไมเขียนแบบนี้ไม่ได้:**
```ts
export function verifyToken(token: string): { sub: string } {
  const payload = jwt.verify(token, authConfig.secret);
  return payload;   // ❌
}
```
```
error TS2322: Type 'string | JwtPayload' is not assignable to type '{ sub: string; }'.
  Type 'string' is not assignable to type '{ sub: string; }'.
```

**ทำไมไลบรารีประกาศว่าอาจคืน `string`** — ไม่ใช่เรื่องงี่เง่า มันเป็นไปได้จริง:
```
sign ด้วย object → verify ได้ : { sub: '42', iat: ... }  | typeof = object
sign ด้วย string → verify ได้ : "ข้อความล้วนๆ"           | typeof = string
```

`jwt.sign` รับ payload เป็นข้อความล้วนก็ได้ ไลบรารีต้องรองรับทุกคน ไม่ใช่แค่โปรเจกต์เรา

### ✅ `as { sub: string }` ยืนยัน 2 อย่าง

| # | ยืนยันว่า | เพราะปกติมันคือ |
|---|---|---|
| 1 | เป็น **object** ไม่ใช่ string | `string \| JwtPayload` |
| 2 | `sub` เป็น **string แน่ๆ** | `sub?: string \| undefined` ← **optional!** |

```ts
export interface JwtPayload {
    sub?: string | undefined;   // ← ไม่การันตีว่ามี
    iat?: number | undefined;
    ...
}
```

### ⚠️ ราคาที่ต้องจ่าย

ถ้าวันหน้ามีคนแก้ `signToken` เป็น `jwt.sign({ userId: ... })` →
`verifyToken` ยังคอมไพล์ผ่าน แต่ `payload.sub` เป็น `undefined` →
`Number(undefined)` = `NaN` → `findById(NaN)` → **ทุกคนล็อกอินไม่ได้ โดยไม่มี error บอกสาเหตุ**

# ส่วนที่ 4 — ทางเลือกที่ปลอดภัยกว่า `as`

```ts
export function verifyToken(token: string): { sub: string } {
  const payload = jwt.verify(token, authConfig.secret);

  if (typeof payload === 'string' || typeof payload.sub !== 'string') {
    throw new AppError(401, 'TOKEN_EXPIRED', 'เซสชันหมดอายุ กรุณาเข้าสู่ระบบใหม่');
  }

  return { sub: payload.sub };
}
```

## 4.1 ✅ บรรทัด `if` เช็คอะไรบ้าง

| ส่วน | เช็คว่า |
|---|---|
| `typeof payload === 'string'` | เป็นข้อความล้วน หรือ object |
| `typeof payload.sub !== 'string'` | **`sub` ตัวเดียว** เป็น string ไหม |

> ⚠️ **ไม่ได้เช็ค `iat` / `exp` / field อื่นเลย** — เราไม่ได้ใช้มัน
> `sub` ตัวเดียวคือทั้งหมดที่ระบบต้องการจาก token

ความหมายเต็ม: *"ถ้าเป็นข้อความล้วน **หรือ** ไม่มี `sub` ที่เป็น string → ไม่ใช่ token ที่ระบบเราออกให้ → โยนทิ้ง"*

## 4.2 Type Narrowing — TypeScript แคบ type ให้เอง

หลักฐาน (บังคับให้ TypeScript เปิดเผยว่าคิดว่าเป็นอะไรในแต่ละจุด):
```
ก่อน if       : string | JwtPayload   ← ยังไม่รู้
หลัง if       : JwtPayload            ← ตัด string ออกแล้ว
payload.sub   : string                ← ตัด undefined ออกแล้ว
```

```
                 string | JwtPayload
                        │
        ┌───────────────┴───────────────┐
   เข้า if (throw)                 ผ่าน if มาได้
   - เป็น string                   - ไม่ใช่ string  → JwtPayload
   - หรือ sub ไม่ใช่ string          - sub เป็น string → { sub: string }
```

**พอถึง `return` TypeScript รู้เองแล้ว จึงไม่ต้อง `as` อีก**

## 4.3 เทียบ `as` vs `if`

| | ถ้าสมมติฐานถูก | ถ้าสมมติฐานผิด |
|---|---|---|
| `as` | ทำงานปกติ | **บั๊กเงียบ** — `undefined` ไหลเข้าระบบ |
| `if` | ทำงานปกติ | **401 พร้อมข้อความ** — รู้ทันที |

**`as` คือการสัญญา · `if` คือการพิสูจน์**

⇒ ใช้ `as` เมื่อ**พิสูจน์ไม่ได้** (เช่น `expireIn` จาก `.env` ไม่มีอะไรให้เช็คตอนรัน)
⇒ ตรงนี้พิสูจน์ได้ง่ายมาก **จึงควรพิสูจน์** — token คือประตูความปลอดภัยของทั้งระบบ 5 บรรทัดคุ้มมาก

# ส่วนที่ 5 — ทำไมไม่ `return payload` เลย

**2 เหตุผล**

## ① TypeScript ไม่ยอม

```
error TS2322: Type 'JwtPayload' is not assignable to type '{ sub: string; }'.
    Type 'string | undefined' is not assignable to type 'string'.
```

**narrowing มีผลกับ expression ไม่ใช่กับ type ของ object**

```
payload      : JwtPayload   ← type ไม่เปลี่ยน ยังมี sub?: string | undefined
payload.sub  : string       ← narrow แค่ตรงนี้
```

⇒ `return { sub: payload.sub }` ผ่านเพราะ**สร้าง object ใหม่จาก expression ที่ narrow แล้ว**

## ② ต่อให้ยอมก็ไม่ควร — ข้อมูลรั่ว

ถ้าวันหน้ามีคนเพิ่ม `role`, `email` ลง payload:

```
return payload         → { sub, role:'admin', email, iat, exp }   ❌
return { sub: ... }    → { sub: '42' }                             ✅
```

- `role` ใน token **ห้ามเชื่อ** (Part 0-1 §1.3) แต่ถ้าคืนออกมา เดี๋ยวมีคนเอาไปใช้
- `iat`/`exp` ไม่มีใครใช้ รกเปล่าๆ

## ⚠️ ถ้าใช้ `as` บังคับให้ผ่าน

```ts
return payload as { sub: string };   // คอมไพล์ผ่าน แต่...
```
**ตอนรันยังคืนทุก field อยู่ดี** เพราะ type หายตอน compile → **type โกหก**

## หลักการเดียวกับ mapper

| | ส่งทั้งก้อน | สร้างใหม่ทีละ field |
|---|---|---|
| mapper | `{...row}` ❌ หลุด `password_hash` | `{ id: row.user_id, ... }` ✅ |
| verifyToken | `return payload` ❌ หลุด `role` | `{ sub: payload.sub }` ✅ |

> **กฎ: ข้อมูลข้ามชั้นเมื่อไหร่ หยิบเฉพาะที่ใช้ อย่าส่งต่อทั้งก้อน**

# ส่วนที่ 6 — Union & Narrowing (สรุป)

## ✅ ความเข้าใจที่ถูก

| | |
|---|---|
| TypeScript ให้มีค่าเดียว? | ❌ union มีหลายค่าได้ ปกติมาก |
| ตอนรันจริงเป็นค่าเดียว | ✅ ถูก |
| `if` ทำให้เป็นค่าเดียว | ❌ **มันเป็นค่าเดียวอยู่แล้ว** |
| `if` ทำให้ TS **รู้** ว่าค่าไหน | ✅ ถูก |

**union = TS ยังไม่รู้ว่าอันไหน · narrowing = ทำให้รู้**

## ก่อน narrow ใช้ได้เฉพาะที่ทุกสมาชิกมีร่วมกัน

```ts
declare const x: string | number;
x.toString();      // ✅ ทั้งคู่มี
x.toUpperCase();   // ❌ มีแค่ string
if (typeof x === 'string') x.toUpperCase();   // ✅
```

> เปรียบเทียบ: union = **รายชื่อผู้ต้องสงสัย** — คนร้ายมีคนเดียวอยู่แล้ว แต่ยังไม่รู้ว่าใคร

## union ที่ใช้อยู่แล้วในโปรเจกต์

```ts
gender: 'male' | 'female' | 'other'    // พิมพ์ 'mail' ผิด → TS ฟ้องทันที
faculty_id: number | null
updated_at: Date | null
```

**narrow ไปแล้วโดยไม่รู้ตัว:**
```ts
return rows[0] ?? null;                                          // user.repo.ts
updatedAt: row.updated_at ? row.updated_at.toISOString() : null;  // user.mapper.ts
```

# ส่วนที่ 7 — `as` บอกอะไรกันแน่ (สรุป)

## ✅ เข้าใจถูกแล้ว
`authConfig.expireIn as ExpiresIn` = บอกว่าค่านี้เป็น 1 ใน `'7d'` / `'15m'` / `'604800'` / `604800` / `'7 days'`

## ⚠️ แต่คือ "เป็นอยู่แล้ว" ไม่ใช่ "ควรจะเป็น"

```
as    → สวัสดี | TS เชื่อว่าเป็น ExpiresIn | ไม่มีใครตรวจ
Zod   → ❌ ไม่ผ่าน
```

| | ความหมาย | ตรวจจริง |
|---|---|---|
| `as` | "เป็นอยู่แล้ว ฉันยืนยัน" | ❌ |
| Zod | "ควรเป็น — ขอตรวจก่อน" | ✅ |

## `type X = ...` ไม่ได้หลอกใคร — เป็นการ**อ่าน**

```ts
type ExpiresIn = NonNullable<SignOptions['expiresIn']>;   // ① อ่านนิยาม
{ expiresIn: authConfig.expireIn as ExpiresIn }           // ② ตรงนี้คือคำสัญญา
```

| | เหมือน |
|---|---|
| `type X = ...` | เปิดพจนานุกรมดูนิยาม |
| `x as X` | เซ็นรับรองว่าค่าตรงตามนิยาม |

## `ExpiresIn` ไม่ใช่ `string` — แคบกว่า

```
error TS2322: Type 'string' is not assignable to type 'ExpiresIn'.
```
```
      string       ← TS รู้แค่นี้ (กว้าง)
        │  as ExpiresIn
        ↓
    ExpiresIn      ← '7d' | '15m' | 604800 | ...
```

⇒ `as` ไม่ได้บอกว่า "เป็น string" (TS รู้อยู่แล้ว) แต่บอกว่า **"เป็น string ที่ format ถูก"**

## นิยามกลางของ `as`

> `x as T` = *"TS มองเห็น x กว้างกว่านี้ แต่ฉันรู้ว่าจริงๆ คือ T"* — **แคบลงเสมอ**

```ts
authConfig.expireIn as ExpiresIn     // format ของข้อความ
jwt.verify(...) as { sub: string }   // หน้าตาของ object
req.user!                            // มีค่าแน่ ไม่ใช่ undefined
```

## เครื่องมือ 2 ตัว ใช้คนละที่

```
Zod → ข้อมูลจากภายนอก (req.body)  → ตรวจจริง เพราะไว้ใจไม่ได้
as  → ข้อมูลที่เราคุมเอง (.env)    → ยืนยันเอา เพราะตรวจตอนคอมไพล์ไม่ได้
```

# 🎁 เกร็ดแปลกที่เจอตอนทดสอบ

ลองตัด `typeof payload === 'string'` ออก เหลือแค่ `if (typeof payload.sub !== 'string')` → **คอมไพล์ผ่านเฉยเลย**

สาเหตุ:
```
typeof "ข้อความ".sub  = function
"abc".sub()           = <sub>abc</sub>
```

**JavaScript มี `String.prototype.sub()` อยู่จริง** — เมธอดโบราณที่ห่อข้อความด้วยแท็ก `<sub>` (ตัวห้อยแบบ H₂O)

⇒ `payload` เป็น string → `payload.sub` = ฟังก์ชัน → `typeof` = `'function'` → ไม่ใช่ `'string'` → throw ✅ **ทำงานถูกโดยบังเอิญ**

## แต่ยังควรเขียน `typeof payload === 'string'` ไว้

1. **บอกเจตนาชัด** — คนอ่านรู้ทันทีว่ากันกรณีไหน ไม่ต้องรู้เรื่องเมธอดโบราณ
2. **ไม่พึ่งความบังเอิญ** — เปลี่ยนชื่อ field เป็นอย่างอื่นเมื่อไหร่ พังทันที
3. **narrowing สะอาดกว่า** — ตัด `string` ออกจาก union ตรงๆ

> เรียง `typeof payload === 'string'` ไว้**หน้า** เพราะ `||` ทำงานซ้ายไปขวาและหยุดทันทีที่เจอ true → เป็น string ก็ throw ตั้งแต่เงื่อนไขแรก ไม่ต้องแตะ `.sub` เลย

# 📌 กฎการใช้ `as` (สรุปเอาไปใช้ต่อ)

## ใช้ได้เมื่อ — คุณรู้มากกว่า TypeScript **จริงๆ**

| สถานการณ์ | ทำไม TypeScript ไม่รู้ |
|---|---|
| `authConfig.expireIn as ExpiresIn` | ค่าอยู่ใน `.env` อ่านตอนรัน |
| `jwt.verify(...) as { sub: string }` | ไลบรารีรองรับหลายกรณี เราใช้แค่กรณีเดียว |
| `req.user!` | ผ่าน `requireAuth` มาแล้ว แต่ TS ไม่ได้ตามดู middleware chain |

## อย่าใช้เมื่อ

- `as any` เพื่อให้เลิกขีดแดง ❌
- cast ทั้ง object (`as SignOptions`) ❌
- ตรวจตอนรันได้อยู่แล้ว → **ตรวจเถอะ** ❌

## 3 ข้อที่ต้องจำ

1. **ไม่แปลงค่า** — ค่าเหมือนเดิมทุกประการ
2. **หายไปตอน compile** — ไม่มีตัวตนใน JavaScript
3. **โกหกได้** — ไม่มีใครตรวจว่าพูดจริงไหม

# ✅ `utils/token.ts` ฉบับสมบูรณ์

```ts
import jwt from 'jsonwebtoken';
import type { SignOptions } from 'jsonwebtoken';
import { authConfig } from '../config/auth.js';
import { AppError } from './AppError.js';

type ExpiresIn = NonNullable<SignOptions['expiresIn']>;

export function signToken(userId: number): string {
  return jwt.sign(
    { sub: String(userId) },
    authConfig.secret,
    { expiresIn: authConfig.expireIn as ExpiresIn }
  );
}

export function verifyToken(token: string): { sub: string } {
  const payload = jwt.verify(token, authConfig.secret);

  if (typeof payload === 'string' || typeof payload.sub !== 'string') {
    throw new AppError(401, 'TOKEN_EXPIRED', 'เซสชันหมดอายุ กรุณาเข้าสู่ระบบใหม่');
  }

  return { sub: payload.sub };
}
```

**ข้อควรระวัง: `utils/token.ts` ต้องไม่รู้จัก `req` เลย**
เคยเขียน `req.user = decode` ในไฟล์นี้ → `Cannot find name 'req'`
ไฟล์ใน `utils/` เป็นฟังก์ชันบริสุทธิ์ รับค่าเข้า คืนค่าออก **ไม่รู้ว่ามี HTTP อยู่ในโลกนี้ด้วยซ้ำ**
การเซ็ต `req.user` เป็นหน้าที่ของ `middlewares/requireAuth.ts`
