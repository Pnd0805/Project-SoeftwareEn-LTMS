# คำถามที่ 1 — `JWT_SECRET` เอามาจากไหน

**คำตอบสั้น:** สร้างเอง ไม่ได้ขอจากใคร มันคือสตริงสุ่มที่คุณคิดขึ้นมาแล้วเก็บเป็นความลับ

## สิ่งที่ควรรู้

**JWT ไม่ได้ถูกเข้ารหัส** — ใครก็เปิดอ่านข้างในได้ (เอาไปแปะที่ jwt.io จะเห็น `{"sub":"42"}` เลย)
สิ่งที่ป้องกันได้คือ **ลายเซ็น** ไม่ใช่การซ่อนข้อมูล

```
token = base64(header) . base64(payload) . ลายเซ็น
                                            ↑
                        HMAC-SHA256(header+payload, JWT_SECRET)
```

- ตอน login → server คำนวณลายเซ็นจาก payload + secret แล้วแปะท้าย
- ตอน verify → คำนวณใหม่จาก payload ที่ได้รับ + secret แล้วเทียบ
- ถ้าใครแก้ `"sub":"42"` เป็น `"sub":"1"` → ลายเซ็นไม่ตรงทันที เพราะเขาไม่มี secret

**⇒ ใครถือ secret = ปลอมเป็นใครก็ได้ในระบบ**

## กฎที่ต้องจำ

| กฎ | เหตุผล |
|---|---|
| ยาว ≥32 ตัวอักษร | สั้นกว่านั้น brute force ได้ (Part 0-1 §1.3) |
| ต้องสุ่มจริง | `mysecret123`, `ltms2026` เดาได้ |
| ห้ามเปลี่ยนพร่ำเพรื่อ | เปลี่ยนเมื่อไหร่ token เก่าใช้ไม่ได้ทั้งหมด ทุกคนหลุดจากระบบ |
| ห้าม commit | `.gitignore` ต้องมี `.env` |
| dev / production คนละตัว | เครื่อง dev หลุด ≠ ระบบจริงหลุด |
| ในทีมไม่ต้องใช้ค่าเดียวกัน | ต่างคนต่างสุ่ม · commit แค่ `.env.example` ที่มี `JWT_SECRET=` เปล่าๆ |

## คำสั่งสุ่ม

```bash
node -e "console.log(require('crypto').randomBytes(48).toString('base64url'))"
```

```bash
openssl rand -base64 48
```

✅ **ทำแล้ว** — `.env` มี `JWT_SECRET` เรียบร้อย

# คำถามที่ 2 — มีแต่ `@types/jsonwebtoken` ไม่มีตัวจริง จะเป็นยังไง

**คำตอบสั้น:** compile ผ่าน แต่รันแล้วพัง — ซึ่ง**อันตรายกว่า**พังตั้งแต่แรก

## สิ่งที่ทดสอบแล้วบนเครื่องจริง

- `node_modules/@types/jsonwebtoken/` มีแค่ `index.d.ts` — **ไม่มีไฟล์ `.js` แม้แต่ไฟล์เดียว**
- `node_modules/jsonwebtoken/` **ไม่มีอยู่**
- ลอง import → `ERR_MODULE_NOT_FOUND: Cannot find package 'jsonwebtoken'`

## ทำไมถึงอันตราย

| ขั้นตอน | ผล |
|---|---|
| เขียนใน VS Code | ✅ ไม่ขีดแดง autocomplete ครบ |
| `npm run typecheck` | ✅ **ผ่าน** |
| `npm run dev` | ✅ ขึ้นได้ (ถ้ายังไม่มีใคร import) |
| มีคนยิง `POST /auth/login` | 💥 **crash** |

**IDE จะบอกว่าโค้ดถูกต้องทั้งที่มันรันไม่ได้**

## แนวคิดหลัก

```
jsonwebtoken/          ← โค้ดจริง  (.js)   Node ใช้ตอนรัน
@types/jsonwebtoken/   ← คำอธิบาย (.d.ts)  TypeScript ใช้ตอนเช็ค
```

เปรียบเทียบ: `@types` = **เมนูอาหาร** · package จริง = **ครัว**
มีเมนูสวยงามบอกว่ามีผัดกะเพรา 60 บาท → สั่งได้ตามเมนู → แต่ไม่มีครัว

## package ไหนต้องลง `@types` ด้วย

| ต้องลง | ไม่ต้องลง |
|---|---|
| `jsonwebtoken`, `bcrypt`, `cors`, `express` | `zod`, `mysql2` |
| (เขียนด้วย JS ล้วน ไม่มี type ติดมา) | (เขียนด้วย TS อยู่แล้ว) |

**วิธีเช็คง่ายๆ:** ลงตัวจริงก่อน ถ้า VS Code ขีดแดงว่า
`Could not find a declaration file for module 'xxx'` ค่อยลง `@types/xxx` ตาม

# คำถามที่ 3 — `bcrypt` กับ `bcryptjs` ตัวเดียวกันไหม

**คำตอบสั้น:** คนละ package แต่อัลกอริทึมเดียวกัน **hash ใช้แทนกันได้ 100%**

## ผลทดสอบจริงบนเครื่องนี้

| ทดสอบ | ผล |
|---|---|
| `bcryptjs` verify hash ที่ `bcrypt` สร้าง | ✅ true |
| `bcrypt` verify hash ที่ `bcryptjs` สร้าง | ✅ true |
| ติดตั้ง `bcrypt` บน Node 24 | ✅ 0.9 วินาที (ใช้ binary สำเร็จรูป ไม่ต้อง compile) |
| ความเร็ว hash 5 ครั้ง | `bcrypt` 214ms · `bcryptjs` 260ms (ต่างแค่ ~20%) |

## ต่างกันตรงไหน

|  | `bcrypt` | `bcryptjs` |
|---|---|---|
| เขียนด้วย | C++ (native addon) | JavaScript ล้วน |
| ตอนติดตั้ง | โหลด binary ถ้าไม่มีจะ compile เอง | ก็อปไฟล์ `.js` เฉยๆ |
| ต้องมี python3/make/g++ | อาจต้อง | ไม่ต้องเลย |
| อัลกอริทึม | **เหมือนกันเป๊ะ** | เหมือนกัน |
| types | ต้องลง `@types/bcrypt` | 3.x มีติดมาในตัว |

**⇒ ใช้ `bcrypt` ต่อไปได้เลย** (แก้ [[03 - Step 0 · ตั้งค่าให้พร้อมรัน]] ให้แล้ว)

## อ่าน hash ให้ออก

```
$2b$10$n.MpmJdB05kCYrg2RTlhr.x.up4gP6TiQDgOoMYB4v2jYBBosKpwy
 └┬┘ └┬┘└──────────┬──────────┘└─────────────┬─────────────┘
  │   │            salt 22 ตัว                hash 31 ตัว
  │   cost = 10 (2^10 = 1024 รอบ)
  version ของอัลกอริทึม
```

**salt ฝังอยู่ใน hash เอง** — นี่คือคำอธิบายของ 2 เรื่องพร้อมกัน:
1. ทำไม hash ถึงใช้ข้ามแพ็กเกจกันได้
2. ทำไม hash รหัสเดิม 2 ครั้งได้ค่าไม่เหมือนกัน แต่ `compare()` ยังทำงานถูก
   (มันดึง salt จาก hash เดิมมาใช้คำนวณ)

## กฎที่ต้องจำ

- bcrypt เป็น **one-way** แปลงกลับไม่ได้
- **ห้ามเทียบ hash ด้วย `===`** ต้องใช้ `compare()` เท่านั้น
- `password_hash VARCHAR(255)` ใน schema กว้างพอ (bcrypt ใช้ ~60 ตัว)
- อยากสลับ package ทีหลัง → เปลี่ยนแค่บรรทัด `import` **ข้อมูลใน DB ไม่ต้องแตะ**

# คำถามที่ 4 — `@types/node` / npm / npx / tsc / tsx

## 4.1 `@types/node` เป็น type ของอะไร

**ของ Node.js เอง** — ต่างจาก `@types` ตัวอื่นตรงที่ไม่มี package คู่ให้ลง

`process`, `Buffer`, `fs`, `path`, `http`, `crypto`, `__dirname` — พวกนี้มีอยู่ใน Node ตั้งแต่แรก
คุณไม่เคย `npm i process` แต่ใช้ `process.env.PORT` ได้เลย

**ปัญหา:** TypeScript ถูกออกแบบให้รันได้ทั้ง browser และ Node → ตัวมันเองไม่ assume ว่าคุณอยู่ที่ไหน

```
@types/node = ไฟล์ .d.ts ที่อธิบายว่า Node.js มีอะไรให้ใช้บ้าง
```

**⇒ นี่คือเหตุผลที่ `"types": []` ใน tsconfig เดิมทำให้ `process.env` ใช้ไม่ได้**

## 4.2 npm คืออะไร

เป็น 3 อย่างพร้อมกัน ใช้ชื่อเดียวกันหมด เลยงง:

| ความหมาย | คืออะไร |
|---|---|
| npm registry | คลัง package กลาง — npmjs.com |
| npm CLI | คำสั่งที่พิมพ์ (`npm i`, `npm run`) ติดมากับ Node |
| npm ecosystem | ระบบทั้งหมดของ JavaScript |

คู่แข่งที่ทำงานแทนกันได้: `yarn`, `pnpm`, `bun` — ดึงของจาก registry เดียวกัน

## 4.3 npx / tsc / tsx ต่างกันยังไง

> **สำคัญสุด: `tsc` กับ `tsx` เป็นคนละ package กันเลย ชื่อคล้ายกันโดยบังเอิญ**

|  | มาจาก | เป็นอะไร | ทำอะไร |
|---|---|---|---|
| **npm** | ติดมากับ Node | ตัวติดตั้ง | โหลด package ลง `node_modules/` |
| **npx** | ติดมากับ npm | **ตัวเรียกใช้** | สั่งรันโปรแกรมใน `node_modules/.bin/` |
| **tsc** | `typescript` | ตัวคอมไพล์ | `.ts` → `.js` + **เช็ค type** |
| **tsx** | `tsx` | ตัวรัน | รัน `.ts` ตรงๆ + **ไม่เช็ค type** |
| **npx tsc** | — | คำสั่งผสม | "npx ช่วยหา tsc ให้หน่อย" |

```
npm  = ไปซื้อเครื่องมือมาเก็บในลิ้นชักของโปรเจกต์นี้
npx  = เปิดลิ้นชักของโปรเจกต์นี้ หยิบเครื่องมือออกมาใช้
tsc  = "เครื่องแปลภาษา"  .ts → .js  + ตรวจไวยากรณ์
tsx  = "ล่ามแปลสด"       อ่าน .ts แล้วรันเลย ไม่ตรวจอะไร
```

**`npx` ไม่เกี่ยวกับ TypeScript เลย** — มันเป็นแค่คนไปหยิบของ จะหยิบอะไรก็ได้

## 4.4 ทำไมต้อง npx ไม่พิมพ์ tsc เฉยๆ

**เครื่องนี้มี `tsc` อยู่ 2 ตัว:**
```
global : ~/.nvm/versions/node/v24.13.0/bin/tsc     ← พิมพ์ tsc เฉยๆ ได้ตัวนี้
local  : soft_end/backend/node_modules/.bin/tsc    ← npx tsc ได้ตัวนี้
```
ตอนนี้บังเอิญเป็น 7.0.2 ทั้งคู่ แต่เป็นไฟล์คนละไฟล์ วันหนึ่งจะไม่ตรงกัน

**⇒ `npx tsc` = ได้เวอร์ชันที่ล็อกไว้ใน `package.json` → ทุกคนในทีมได้ผลเหมือนกัน**

## 4.5 เกร็ดที่ทำให้ชีวิตง่าย

**ใน `package.json` scripts ไม่ต้องใส่ `npx`** — `npm run` เติม `node_modules/.bin/` เข้า PATH ให้เอง

```json
"scripts": {
  "build": "tsc",                      ← ได้ตัว local อยู่แล้ว
  "dev": "tsx watch src/server.ts"
}
```

| สถานการณ์ | พิมพ์ |
|---|---|
| งานประจำของโปรเจกต์ | `npm run dev` / `npm run build` |
| รันเครื่องมือครั้งเดียว ไม่อยู่ใน scripts | `npx tsc --noEmit` |
| ลองเครื่องมือที่**ยังไม่ได้ลง** | `npx create-vite my-app` (โหลดชั่วคราวแล้วลบ) |

## 4.6 tsc vs tsx — ตารางเทียบ

|  | `tsc` | `tsx` |
|---|---|---|
| สร้างไฟล์ `.js` ไหม | ✅ สร้าง | ❌ ไม่สร้าง |
| เช็ค type ไหม | ✅ เช็ค | ❌ **แค่ลบ type ทิ้ง** |
| ความเร็ว | ช้ากว่า | เร็วมาก (ใช้ esbuild) |
| ใช้ตอนไหน | จะ deploy จริง | ตอนพัฒนา |
| ในโปรเจกต์นี้ | `npm run build` | `npm run dev` |

```ts
const port: number = "8000";   // type ผิดชัดๆ
console.log(port);
```
- `tsx` → พิมพ์ `8000` ออกมาเฉยๆ **ไม่บ่น**
- `tsc --noEmit` → ❌ error ทันที

> ⚠️ **กับดักชื่อ:** package `tsx` ไม่เกี่ยวกับนามสกุลไฟล์ `.tsx` (React) เลย
> `tsx` ย่อจาก **T**ype**S**cript **E**xecute

# 🎯 บทเรียนที่ใหญ่กว่าคำถาม

## 1. "compile ผ่าน" ≠ "รันได้"

เจอ 2 ครั้งในวันเดียว:
- `@types` อย่างเดียว → typecheck ผ่าน แต่ `ERR_MODULE_NOT_FOUND` ตอนรัน
- `tsx` → รันได้ แต่ type ผิดก็ไม่บอก

**⇒ ต้องทำทั้ง 2 อย่างเสมอ: `npm run typecheck` + ทดสอบยิง API จริง**

## 2. dependency กับ devDependency คนละหน้าที่

```
dependencies     → โค้ดที่รันจริงตอน production ต้องใช้
                   jsonwebtoken, bcrypt, zod, cors, express, mysql2, dotenv

devDependencies  → เครื่องมือสำหรับพัฒนาเท่านั้น
                   typescript, tsx, @types/*
```

`@types/*` อยู่ใน dev ได้เสมอ เพราะตอนรันจริงไม่มีใครใช้ type แล้ว (มันถูกลบทิ้งไปตอน compile)

## 3. อย่าเชื่อคำแนะนำทั่วไปโดยไม่ทดสอบเครื่องตัวเอง

เคส `bcryptjs` — คำแนะนำมาตรฐานบอกว่า "bcrypt ติดตั้งพังบ่อย ใช้ bcryptjs ดีกว่า"
พอทดสอบจริงบนเครื่องนี้: bcrypt ลงผ่านใน 0.9 วิ และเร็วกว่าแค่ 20%
**⇒ แก้เอกสารตามความจริงที่วัดได้ ดีกว่าเชื่อตามที่คนส่วนใหญ่พูด**
